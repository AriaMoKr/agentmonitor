# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

agentmonitor: the Claude Code sessions on this computer (in a terminal, the desktop app's Code tab, an IDE, the background) that run or were active lately, with what each is doing, its task list and the subagents and workflows it started, and how much of the plan's usage limits is used (as the desktop app last sampled it, carried on to now with this computer's replies) and about when they reset, live in a terminal, or with `--serve` as a web page, which another computer can open, or in `desktop/` as an Electron app with a window and a tray icon. Node 22 or later, plain ES modules, no dependencies (but Electron, in `desktop/` only) and no build. `README.md` covers using it, what it reads and how it decides a session's state.

## Commands

```bash
node bin/agentmonitor.js          # full screen; q quits
node bin/agentmonitor.js --once   # the table, printed once (also when stdout is not a terminal)
node bin/agentmonitor.js --json   # what was found, as JSON (without the events)
node bin/agentmonitor.js --serve  # the web view, at the address it prints; Ctrl+C stops it
npm test                          # node --test "test/*.test.js"
cd desktop && npm install && npm start   # the desktop app; npm start -- --quit quits it
```

## Layout

- `bin/agentmonitor.js`: the options, then `runTui`, `serve`, or one table or JSON.
- `src/monitor.js`: `Monitor.refresh(now)` puts a `Snapshot` together: sessions (one row per process running one, or one for a session that ended), each with its subagents and workflow runs as `children`, a workflow's agents as its children; and `usage`, the plan's usage as the desktop app last sampled it, and as carried on to now (`tracked`). With `wait`, a refresh waits for what is read in the background (the replies): for `--once` and `--json`. `focus` holds the keys of the agents whose transcripts are read though they are not at work (those selected: the terminal's, and each web page's).
- `src/registry.js` (`sessions/<pid>.json`), `src/transcript.js` (a transcript read as it grows), `src/agents.js` (a session's subagents and workflow runs), `src/jobs.js` (`jobs/*/state.json`), `src/desktop.js` (the desktop app's session records: its summary of each one's last turn, and from them which sessions it shows unread), `src/usage.js` (the app's samples of the plan's usage, read at most every 5 seconds and worked out again only when the file changed: `usageOf` takes the latest, and the resets from the samples of its org, each as `{ at, from, to }`, the likeliest and the range: `sessionReset`, five hours after the window began, on the 10-minute mark at or before its first use, where the percent rose from 0 (likeliest that of the last 0) or dropped (the first mark after); `weekReset`, the time of the week two drops or more agree on, on the hour in it; `track` carries the latest sample on to now with the replies, each percent at as many points for so much use as its latest rises came to, each between two samples at most 30 minutes apart: the session's only rises within a window the replies began (on the mark at or before the first reply asked for once the last one ended), and its reset that window's end, to the minute; the week's only with its reset known; and in a window `sessionPace`, the points the last hour's replies came to as an hour's worth, once 15 minutes of them are known; `repliesSince`, how far back the replies are needed), `src/ledger.js` (the replies in every transcript under `projects/` since a time: each message once, by `message.id`, at its first record's time and asked for `thinkingDurationMs` before; its tokens weighed against output (input as the API prices it, cache reads and writes as the app's samples rose with them), and its model against Claude Opus 5.5, another provider's at 0; read in the background at most every 10 seconds, a transcript not read yet from near that time by a binary search on its records' times, then only what was appended), `src/procs.js` (is a PID running, and is it Claude Code), `src/files.js` (folders and JSON read again only when changed).
- `src/view.js`: what is drawn, as lines for a screen size, and where a click on them goes (`hits`: a row selects it, a session or an agent in the panel below the rows opens its details, the rest of the space below the rows selects none, a title sorts by it, a key is pressed): pure, so the tests draw it. `panelLines` fills the room the rows leave: a blank line, the selected agent (`previewLines`, 8 lines at most), the other sessions that need you (`needsItems`, whole items only), what was said lately in the sessions listed (`feedLines`), and at the bottom the usage (`paceLines`: a bar marked where the limit's time has gone to, its reset, its pace and when that reaches 100%); the room goes first to the usage, then to the selected agent, then to what needs you, and what was said takes the rest. `shown(a)` is the state a row shows: blocked, unread, in a tool, `background` (idle while a command, an agent or a workflow it started goes on), else its own. With none selected `ui.index` is -1, and stays so as rows come and go, until a key or a click selects one. Its theme says whether it is for a web page (`t.web`: text selected by dragging), and which keys quit (`t.quit`, as the help lists them: none on a web page, q in the agentmonitor app's window). `header` is the first line, of parts each with a worth: where they don't all fit, the least worth go first (the time; the sessions ended and the agents at work; the title and the sessions idle, in the background or active; those at work and the resets; those waiting; the usage last), then of those as many come back as fit, the most worth first. A reset is attached to its percent, with one space between, and goes when it goes. `wrapStyled` wraps a line with styles to a width, under an indent, a style closed at a break and opened again (a no-break space keeps words together, drawn as a space): the help's lines, on a screen narrower than 88 columns, and the panel's. `src/viewer.js`: one look at the monitor (the view shown, the selection, the filter, the bell) and what keys and clicks do to it; the terminal has one, and the web view one per page. Its `focus` is the selected agent, in the list or in its details, and `onFocus` is told when that changes, after a key, a click or the rows moving it. `rings(snap)` is the bell's rule (a session starts waiting, or goes from working to idle, while `b` has the bell on), told every read so that turning it on never rings for what changed before. `src/tui.js`: the alternate screen, the keys and the mouse (`src/keys.js`; the terminal's reports in the SGR form, asked for with modes 1000 and 1006), the timers, painting the lines that changed, and every 2 seconds all of them (a terminal can lose lines without telling the program: the desktop app's Terminal panel has). `src/format.js`: terminal-safe text, widths, short forms.
- `src/serve.js`: the web view's server (`node:http`): the page's files and `screen?page=<id>&w=&h=&i=<input>...`, which applies the inputs to that page's `Viewer` (`f:<text>` is the filter as typed in the page's text field, `Viewer.typeFilter`; `t:up` or `t:down`, a finger dragged a line's height, `Viewer.drag`: the list's selection goes with it, the details' and the help's text too) and answers `{ title, bell, ring, lines, keys, filter, typing }`: the title (with how many sessions wait for you), whether its bell is on and rings now, its lines as JSON runs (`[text, classes, columns]`: the SGR styles made classes, characters outside ASCII with their width), where a click presses a key (`[line, from, to, key]`), and the filter and whether it is being typed; with `quiet=1`, only the first three. With `onQuit`, which the agentmonitor app gives, q quits as in a terminal: the page is answered without its lines, then `onQuit` is called. A read is shared by the pages and made when one asks and the last is older than the interval. `urls()` lists the addresses to open it at, the likeliest for a phone first (virtual networks' last: an address ending in .1, a hypervisor's MAC), and `banner()` is what `--serve` prints, with a QR code of the first for a phone's camera when it listens beyond this computer and has colors (`src/qr.js`: byte mode, level M, versions 1 to 10, the mask the standard's penalty scores best; drawn black on bright white with ▀, two rows of modules a line). `src/web/`: the page (`index.html`, `app.css`, and `app.js`, which asks each second, or quietly every 3 while out of sight, draws the lines that changed, sends keys, clicks, the wheel and a finger's drags, and beeps with Web Audio when the bell rings, once a tap, click or key has let it. A phone shows its keyboard only for a focus in a tap, so a tap on `/` focuses the page's hidden text field at once, and the lines are measured against `visualViewport` to stay above the keyboard; its pure helpers are exported for the tests).
- `desktop/`: the agentmonitor app, with Electron; its main process is `main.js`, an ES module. It runs `serve()` in its process (127.0.0.1, port 0, a token of its own) and shows the page in a `BrowserWindow`, where q quits (`onQuit`); the tray asks `served.snapshot()` every 2 seconds, the page's read shared. One runs at a time (a second start shows its window, or with `--quit` quits it); `--hidden` starts it in the tray (`paintWhenInitiallyHidden` off, so the page starts out of sight and quiet). Closed or minimized, the window goes to the tray. Its settings (`notify`, `minimizeToTray`, `zoom`, `launcher`, `toldTray`, `bounds`, `maximized`) are `settings.json` in its userData folder, read back checked. The first start writes the Start menu's shortcut (with the app's ID, `agentmonitor`, which Windows' notifications need) or Linux's `.desktop` entry, and keeps it up to date unless taken out from the menu; start at login is Electron's login item on Windows, an autostart entry on Linux, and not offered on macOS (it would start bare Electron). `tray.js` (pure): `trayState` (the level, what matters most: waiting, unread, working, background, idle or none; the counts, the usage, the tooltip, the sessions the menu lists) and `notices` (the bell's rule, `ringing` from `src/viewer.js`). `icons.js` (pure): the icons drawn in code (shapes on a 16-unit grid, antialiased) as PNG and ICO, each image in four scales for the screen's. `launch.js` (pure): a freedesktop entry.
- `test/helpers/fixture.js` writes a config folder as Claude Code does (times relative to `NOW`, mtimes set); `test/helpers/screen.js` is a fake TTY pair and a screen that applies what is written; `test/helpers/agents.js` makes agents and snapshots by hand.

## Claude Code's files

Undocumented, read as Claude Code 2.1.3xx writes them; a new version can change them, so a field that is missing or of another type is skipped, never an error.

- `sessions/<pid>.json`: `pid`, `sessionId`, `cwd`, `startedAt`, `procStart` or `procStartFt`, `version`, `kind` (`interactive`, or a background kind), `entrypoint` (`cli`, `claude-desktop`, `claude-vscode`, `sdk-*`, `local-agent`...), `hostSessionId` (the desktop app's `local_<id>`), `pidDomain` (`win32:<host>` on Windows), `name` and `nameSource` (`derived`: made from the prompt), `status` (`busy`, `waiting`, `idle`) with `waitingFor` and `statusUpdatedAt`, `jobId`, `spare` (a process started ahead of a session).
- Transcripts, one JSON record per line: `user` and `assistant` (with `uuid`, `timestamp`, `cwd`, `gitBranch`, `version`, `entrypoint`, `permissionMode`). An assistant message is written one record per content block, each with the same `message.id` and the usage so far: count its output tokens once. That `message.usage` has `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`; `message.model` is the model (another provider's, through a proxy, or `<synthetic>`). A thinking block's record, written when the thinking ends, has `thinkingDurationMs` at its top. Assistant records carry `effort` (the session's: `low`, `medium`, `high`, `xhigh`, `max`) and `perTurnEffort` (the turn's; the same so far, or null in older versions). API errors are assistant records with model `<synthetic>` and `isApiErrorMessage`; a usage limit's (`error: 'rate_limit'`) has `quotaLimits` with `rateLimitType` (`five_hour`, `seven_day`) and `resetsAt` (seconds). An `attachment` record of type `ultra_effort_enter` (`reminderType` `full` or `sparse`) is ultracode's reminder: after the first prompt, about every tenth since and after a compaction, only while the desktop app's setting is on (none came with a prompt naming ultracode); no record says it was turned off. `mode` and `atis-latch` records say nothing of it. Also `custom-title`, `ai-title`, `agent-name`, `summary`, `last-prompt`, `cost-state` and `system` (`compact_boundary`). `cost-state`, `last-prompt` and `bridge-session` have no time and are appended to every open transcript when the app quits: take times from records, never from the file's mtime. Records the monitor never needs (`api-request`, `file-history`, ...; some are megabytes) are skipped by their first bytes, unparsed.
- Tool calls in transcripts that the monitor follows, each from its call to its result (a result that is an error changes nothing):
  - Calls that wait on the user: `AskUserQuestion` (`questions[]` with `question`, `header`), `ExitPlanMode`, and `mcp__ccd_session__start_session` with `initiation: 'offer'`. The desktop app's permission prompts are in no file.
  - The task list: the desktop app's `mcp__ccd_turn__update_plan`. `items` (`content`, `status`: `pending`, `in_progress`, `completed`) replaces the list, and any `advance`, `done` or `start` in the same call is then ignored. `advance: true` completes the step in progress and starts the next pending one; `done: [n]` and `start: n` count from 1. `mcp__ccd_turn__wrap_up` checks off the step in progress. Claude Code's own list is `TodoWrite` (`todos[]` with `content`, `status`, `activeForm`).
  - Commands in the background: a call whose result begins `Command running in background with ID: <id>`, or `Command did not complete within its <n>s timeout and was moved to the background (ID: <id>)`. Its end is a `<task-notification>` (with `<tool-use-id>` and `<status>`), as a `user` record's string content, or, when it came in during a turn, in an `attachment` record of type `queued_command` (its `prompt`). `TaskStop` (`task_id`) or `KillShell` (`shell_id`) stops one.
- `<session>/subagents/agent-<id>.meta.json`: `agentType`, `description`, `toolUseId` (the Agent call in the session's transcript), `requestShape` (`foreground` or `background`); only a background one gets `finished` or `stoppedByUser`.
- Workflows: `<session>/subagents/workflows/<run>/` (agents, as subagents, with `workflowPhase` in their meta; `journal.jsonl`: `started` with `agentId`, `label`, `phase`, then `result` or `failed`), `<session>/workflows/<run>.json` once it ended (`status`, `workflowName`, `startTime`, `durationMs`, `totalTokens`, `defaultModel`), `<session>/workflows/scripts/<name>-<run>.js`.
- `jobs/<id>/state.json`: `sessionId`, `name`, `state`, `detail`, `needs`, `cwd`, `createdAt` and `updatedAt` (ISO), `cliVersion`.
- The desktop app's `claude-code-sessions/<account>/<org>/local_<id>.json`: `sessionId`, `cliSessionId`, `title`, `cwd`, `isArchived`, `model`, `effort`, `permissionMode`, `sessionSettings` (`ultracode: true` while ultracode is on; no `sessionSettings` when nothing was set, or for a session started elsewhere), `createdAt`, `lastActivityAt`, `lastFocusedAt` (when the session was last opened in the app, overwritten each time) and `lastTurnEdgeAt` (when a turn last started or ended). `postTurnSummary` is the app's summary of the last turn, written a few seconds after it ends and not after every one: `status_category` (`completed`, `blocked`, `review_ready`), `status_detail`, `needs_action` (empty unless blocked) and `summarizes_uuid` (the transcript record it sums up, also in `postTurnSummaryFor`). It is used only for a session not at work, and only when it names the transcript's last assistant record. The app keeps its unread list (its blue dots) in its own browser storage: `epitaxy-unread-v1` in its Local Storage (`unreadIds`, and `explicitUnreadIds` for the dots set by hand). The monitor never reads that. It works out the same list from these two fields: a session is unread when it is not at work, its last turn ended after its last opening, and another session was the last one opened when that turn ended.
- The desktop app's `plan-usage-history.json`, in the folders of its session records: `version` (2) and `samples[]`, each with `t` (ms), `org` and `u`: `fh`, the percent of the plan's five-hour limit used (the session), and `sd`, of its seven-day one (the week). One about every 15 minutes while the app runs (with pauses of hours at times), none while it does not, about 30 days of them; whole numbers so far, 100 at most. No reset times: the week's limit resets at a fixed time of the week (Thursday 10:00 UTC on the account it was worked out on), the session's five hours after the 10-minute mark at or before its first use (every `resetsAt` of the limit errors in the transcripts was on one, and the replies' first ones fit); the percents show both, rising from 0 or dropping. The app's `config.json` beside it holds its sign-in (`oauth:tokenCache`): never read it. `~/.claude.json`'s `cachedUsageUtilization` has the reset times, but only `/usage` refreshes it, and the file holds the account's settings: not read either.

## Rules

- Read only: never write under the config folder or the desktop app's, never signal a process but with signal 0. Read only the files above; never `.credentials.json`, the desktop app's `config.json` or anything else there.
- No dependencies, but Electron for the agentmonitor app: only in `desktop/package.json`, and only `desktop/main.js` imports it, so the tests run without it. Its window is the web view's page and nothing else: sandboxed, context isolated, no Node, no other window or address, every permission denied. It writes only its own folder, its menu entry and, when asked, its login item.
- Keep it portable (Windows, macOS, Linux): paths in the data can be any system's (`lastPart`, `relativeTo`), processes come from `tasklist` or `ps`, and commands in docs are POSIX shell.
- All text from the files is untrusted terminal output: through `clean()` before it is drawn, and measured with `width()`, `fit()` and `truncate()` (wide characters, emoji). With `--ascii`, draw nothing but ASCII of the monitor's own (`t.sep`, `t.ellipsis`, `t.pad`).
- The screen: autowrap off, and the last line one column short, since writing the bottom right cell scrolls some terminals. Every way out puts the terminal back, with its mouse reports off.
- On Windows, Node's raw mode is the console's VT input, and the console passes the mouse's modes (1000, 1006) on to the terminal only while that is on, and does not turn them off when Node exits: raw mode on before asking for the mouse, the mouse off before leaving raw mode. In mintty Node gets pipes, not a console, so there is no full screen there. `msys2_shell.cmd -defterm -here -no-start -ucrt64` runs MSYS2's bash in the console it is started from.
- The web view stays read only and private: GET and HEAD only; every path under the token (compared in constant time), anything else 404; 127.0.0.1 unless `--host` says otherwise. The page runs its own script and style and nothing inline (its Content-Security-Policy forbids the rest), puts what it gets in with `textContent` and classes, never `innerHTML` or a style attribute, and keeps nothing (`no-store`, no cookies). A page's inputs move only its own view (but `w`, the shared window, and q in the agentmonitor app's window, which quits it).
- Keep a refresh cheap: transcripts are read from their tail and then only what was appended; for the usage, their replies in the background, at most every 10 seconds, from those written since the time needed, and then only what was appended; JSON files are parsed again only when their size or mtime changes; the process table is read for a new PID and every 10 seconds.
- Tests: `node:test`, a fixture config folder with fixed times, the TUI through the fake terminal, the web view through real requests to 127.0.0.1 on a free port (never 0.0.0.0, which makes Windows ask about its firewall), QR codes against the standard's own values and codes another encoder made (qrcode-generator), as no reader is at hand, the agentmonitor app's pure parts without Electron (`test/tray.test.js`; its icons decoded and their CRCs checked). Run `npm test` before a commit.
- Style: ES modules, JSDoc types, single quotes, a header comment in each file saying what it is for.
